G1 Deployment Day

The order to do things in, and what each step is actually worth. Every step below was either executed against a MuJoCo G1 on the DDS bus, or is marked as something that cannot be.

This bundle has been on a G1 once — INIT and the fixed stand, in a gantry harness, on 2026-09-11, with the policy never armed. Every number here is simulation. This procedure cannot make a first hardware run safe — it can only stop you discovering a software problem while the robot is powered.

PHASE 0

The machine, the day before

On the machine you will deploy from — the TensorRT engine is built per-machine and cached.

  • 10.13 on x86_64, 10.7 on the robot's own Orin. Not a formality: the engine-vs-ONNX mean disagreement is 1.45e-06 at 10.13 and 1.10e-04 at 10.16 — 76× worse at the wrong version.

    source env.sh          # must print TensorRT 10.13
ldd runner/target/release/g1_deploy_onnx_ref | grep cudart   # .so.12

  • Measured: 7 pass, 0 fail, 1 warn. The warn is check 8, the start-pose step, and it is expected — see 4.2. Any FAIL stops the day.

    bash test.sh

  • Measured on deploy_dr, TensorRT 10.13.3, FP32, 499 ticks: max |delta| 6.2e-06, mean 4.2e-07.

    Record the baseline per policy. deploy_dr sits near 2e-06 mean and no_dr near 6.9e-05 on the same correctly-pinned install — a 33× spread that is a property of the networks, not the machine. Judge a new export against its own first reading.

    bash drill.sh --play --parity

  • The runner loads a 55 MiB engine and needs a CUDA context on top. Attempted on a 32 GB card with training jobs holding it, this failed two different ways:

    183 MiB free → OOM reading the engine → std::runtime_error → SIGABRT
168 MiB free → CUDA init error 2      → "Unable to set GPU device 0" → SIGSEGV
    Fail-safe, but not loud

    Both abort in the constructor at :2300, before the input interface exists at :2510 and before any DDS write — the simulator read lowcmd=no throughout both, so the robot is never driven. But one path is a segfault, and neither says "the GPU is busy". Do not share the deploy machine's GPU with training jobs.

  • INIT ramp, ~5.5 s of fixed stand, the policy takes over, the robot goes down, the stop. If you have not watched this in simulation, do not watch it for the first time on a robot.

    bash drill.sh --play --viewer      # needs a desktop session
PHASE 1

The network

  • sudo ip addr add 192.168.123.222/24 dev enp3s0
sudo ip link set enp3s0 up
ping -c3 192.168.123.161
sudo tcpdump -i enp3s0 -c 20 udp portrange 7400-7500

    Silence on the tcpdump means DDS is not flowing. Fix it before anything else — the runner otherwise sits forever printing LowState is not available, which looks like a hang and is correct behaviour.

  • With no 192.168.123.x interface present it refuses rather than falling back: no 192.168.123.x interface found. Releasing Unitree's own controller happens inside the runner at construction and can take several seconds on a real G1.

PHASE 2

Safety

None of this is in the software, and none of it can be rehearsed.

  • The runner's stop path is a software boolean plus a 35 rad/s joint-velocity abort and a motor-temperature cutoff at 90 °C. None of those is an emergency stop. For a humanoid, cutting power is itself a hazard, because the robot falls.

  • With slack for the motion. Required from Init Done onward, not just during the policy.

  • Nobody inside the reachable volume. One thing here is rehearsed: run.sh reads its safety checklist from /dev/tty, not stdin, so a pipe cannot answer it — with no controlling terminal it refuses rather than arming a robot with nobody in the room.

PHASE 3

The dry run — power on, stand, do not arm

The first run with the robot powered should never reach the policy.

  • bash run.sh --policy deploy_dr --iface enp3s0 \
       --motion walk_arc_cw_stop_001__A047
    Always pass --motion

    Which clip is motion index 0 is not defined. motion_data_reader.hpp:685 enumerates the directory with an unsorted std::filesystem::directory_iterator, so it is readdir order and machine-dependent. Measured here the clips come back walk_ff, walk_arc, crouch_idle — not alphabetical, and not the order any listing shows you. Pinning one clip is the only way to know what T will play.

  • Holding default_angles at the runner's own gains, unsupported, the robot sits down in about 1.4 s in MuJoCo — ankle pitch (28.5 N·m/rad, derived from rotor inertia, not from the balance moment) cannot hold the balance torque. The vendor's own sim config ships ENABLE_ELASTIC_BAND: True for this reason.

    This is a simulation result about a simulation model. It does not prove a real G1 falls over. Treat it as a reason to have the harness on.

  • The step the procedure wanted, and the runner does not have

    Pressing F during the fixed stand does nothing. The temperature handler sits inside case ProgramState::CONTROL (:3859), and so does the Loop timing print (:4049). Rehearsed: F through the whole stand produced not one line.

    So in WAIT_FOR_CONTROL there are no motor temperatures, no LowState age, no loop timing. A dry run establishes only that the engine loaded, that LowState is arriving (else Init Done never prints), and that nothing errored.

    Consequence for sequencing: you cannot measure the realised control period before arming. Those numbers first exist when the robot is already under policy control — so have someone watching the console whose only job is those lines. Measured once armed: LowState age 2.2–23.0 ms, policy inference 2.1–11.2 ms. Note 11.2 ms is over half the 20 ms budget a 50 Hz loop has.

  • exitwhat it doesleaves the robot
    Ojoins threads, writes one damping command kp 0, kd 8, tau 0limp — it goes down
    Ctrl-CSIGINT. The runner installs no signal handlerholding the last command, nothing driving it

    Rehearsed: SIGINT was sent during the fixed stand. The runner's log ends at Init Done — no Stopping G1Deploy, no Stop — and the simulator went on reporting lowcmd=yes kp[0]=99.1 kd[0]=6.3 with the pelvis at 0.759 m for as long as it was watched.

    Do not assume that is benign

    In MuJoCo the robot kept standing because the simulator applies the last LowCmd forever and the band was on. A real G1's motor controller may have its own watchdog that does something else when commands stop. This bundle cannot tell you which.

    On a supported robot, O is the exit to use — it is the one that leaves a defined command on the wire. If you do hit Ctrl-C, run stty sane: the destructor that restores your terminal never ran either.

PHASE 4

The first armed run

  • ] hands the policy frame 0 of the reference, and all three shipped clips start far from the pose the runner holds. Start with the smallest.

    clipRMS, 29 jointsworst leg joint
    walk_arc_cw_stop_001__A0470.299 radL_knee −0.548
    walk_ff_stop_270_R…__A445_M0.341 radR_knee −0.546
    crouch_idle_004__A2460.409 radR_hip_pitch −0.816

    The policy must close that in one control step, standing, on its feet — a step it never sees in training, where every episode resets onto the reference with its velocities.

  • ']'   arm    WAIT_FOR_CONTROL → CONTROL. Policy runs at 50 Hz,
             reference parked at frame 0. THIS ALONE DOES NOT PLAY THE CLIP.
'T'   play   run the clip from the current frame to its end.

    A policy left armed but unplayed tracks a still pose and looks like it is failing. T is the only key that sets operator_state.play.

  • FIXED STAND   0.759 → 0.769 m   held 5.5 s   kp 99.1  kd 6.3
POLICY        0.768 → 0.373 m   travelled 0.27 m
AFTER STOP    0.063 → 0.064 m                kp 0.0   kd 8.0

    The reference clip walks an arc; the robot travelled 0.27 m. That gap is the missing horizontal-position term — the observation has none at all, so the policy cannot tell it is off the path. Treat every deployment as open-loop in the horizontal plane.

  • The one safety property in here that works the way you would want. The simulator was SIGKILLed mid-policy — on hardware, a pulled cable or the robot powering off under you:

    [ERROR] Lost LowState data connection from robot!
[ERROR] Safety check failed, stopping control.
[DEBUG] Stopping G1Deploy...  →  Stop

    It goes through Stop(), so the damping command is written. Note what that means physically: the correct response to losing the robot is to make it go limp. If the cable pulls mid-motion, the robot goes down. That is the right call and it is still a fall.

PHASE 5

Stop, and what recovery actually is

  • operator_state.stop is set in four places and cleared in none; program_state_ only ever moves forward; and main is while (!operator_state.stop) { sleep(0.02); }. There is no key that goes back to a stand. Confirmed in every rehearsal.

  • tpelviskp[0]
    44.7 s0.061 m0cycle 1 stop — on the floor
    68.8 s0.064 m99.1cycle 2 INIT ramp begins, on a fallen robot
    78.9 s0.133 m99.1still down — and the runner printed Init Done
    Init Done is a timer, not a measurement

    InitControl() interpolates for duration_ = 3 s and declares itself finished. Nothing checks that the robot is upright, that default_angles is reachable, or that the feet are under the body. It then transitioned to CONTROL and played a whole clip to completion, reporting every marker normally, with the robot flat on the ground. A person has to put the robot back on its feet.

  • standby.sh pins one clip per launch, runs it through run.sh, and gates every cycle on someone confirming the robot is upright and supported. It adds nothing to the runner — each cycle is an ordinary run.sh, and the restart is what re-enters INIT.

    bash standby.sh --iface enp3s0
REF

Operator keys

keyeffect
]arm — WAIT_FOR_CONTROL → CONTROL. Arms only; does not play.
Tplay the clip from the current frame to its end
Oemergency stop — kp 0, kd 8, tau 0. Terminal.
N / Pnext / previous motion
Rreset the clip to frame 0, paused
Ireinitialise heading from the current IMU
Fmotor temperatures — only while armed; silent in the stand
Ctrl-Ckills the process — no damping command, terminal left raw

Lower case works for all of them except ]. The Unitree wireless remote is supported unmodified via --input-type gamepad (or manager for both at once): Start = ], Select = O, A = T, B = R, L1/R1 = P/N. The bundled simulator does not publish wireless_remote, so the remote cannot be rehearsed — the first button press would be on the robot.

What this procedure still does not establish

  1. Anything about how a POLICY behaves on a robot. The one hardware run reached the fixed stand under a gantry and stopped there; ] was never pressed.
  2. That the fixed stand holds an unsupported G1. In simulation it does not.
  3. That a policy survives the step at ]. In simulation it does not.
  4. That the wireless remote works — it cannot be rehearsed in this bundle.
  5. Recovery has no calibrated band, dwell or horizon, so no policy has passed or failed a recovery test. "0/16 falls" is a measurement on one clip, not a safety property.
